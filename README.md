# Практическая работа: как работает DNS

Эта работа выполняется **без компьютера**.

Вам понадобятся только:

- тетрадь;
- ручка;
- этот материал.

Цель работы — не просто запомнить названия DNS-записей, а понять, **что происходит от момента ввода имени до подключения к нужному серверу**.

После выполнения вы должны уметь:

- объяснить, зачем вообще нужен DNS;
- отличать IP-адрес, доменное имя и URL;
- понимать, кто именно выполняет DNS-запрос;
- объяснить разницу между рекурсивным и авторитетным DNS-сервером;
- понимать, что такое домен, поддомен, FQDN и DNS-зона;
- различать записи A, AAAA, CNAME, MX, NS, PTR и SOA;
- читать простую DNS-зону;
- понимать работу кэша и TTL;
- объяснять прямое и обратное разрешение имён;
- находить типичные логические ошибки в DNS;
- объяснять ситуацию «по IP работает, по имени — нет».

## Как выполнять работу

Сначала прочитайте всю теоретическую часть.

Не переходите сразу к заданиям: почти каждое из них опирается на объяснения ниже.

Все задания выполняйте **письменно в тетради**.

3. короткое объяснение, если оно требуется.

Если нужно составить DNS-запись, используйте понятный формат:

~~~text
имя    тип    значение
~~~

Например:

~~~text
app.lab.test    A    10.0.0.15
~~~

# 1. Зачем нужен DNS

Компьютеры передают данные по сети, используя IP-адреса.

Например:

~~~text
10.0.0.15
~~~

Человеку неудобно помнить IP каждого сервера.

Намного удобнее использовать имя:

~~~text
app.lab.test
~~~

DNS — **Domain Name System**, система доменных имён.

Её одна из главных задач:

~~~text
доменное имя → IP-адрес
~~~

Например:

~~~text
app.lab.test
      │
      │ DNS
      ▼
10.0.0.15
~~~

После получения IP клиент уже может обращаться к нужному компьютеру.

Важно:

> DNS не передаёт веб-страницы, файлы или сообщения. DNS помогает найти адрес нужного узла.

Можно представить DNS как справочную службу.

Вы спрашиваете:

~~~text
Где находится app.lab.test?
~~~

DNS отвечает:

~~~text
10.0.0.15
~~~

После этого дальнейшее соединение происходит уже с этим IP.

---

# 2. IP-адрес, доменное имя и URL — это не одно и то же

Студенты часто смешивают эти понятия.

## IP-адрес

Это сетевой адрес.

Например:

~~~text
192.168.1.20
~~~

или IPv6:

~~~text
2001:db8::20
~~~

## Доменное имя

Это имя в системе DNS.

Например:

~~~text
portal.example.test
~~~

DNS может связать это имя с IP-адресом.

## URL

URL описывает, **к какому ресурсу и по какому протоколу** мы обращаемся.

Например:

~~~text
https://portal.example.test/news/index.html
~~~

Здесь:

~~~text
https                    → протокол
portal.example.test       → доменное имя
/news/index.html          → путь к ресурсу
~~~

DNS работает именно с именем:

~~~text
portal.example.test
~~~

а не со всем URL целиком.

---

# 3. Что происходит, когда пользователь вводит имя

Представим, что пользователь хочет открыть:

~~~text
portal.example.test
~~~

У приложения пока есть только имя.

Для сетевого подключения нужен IP.

Упрощённо процесс выглядит так:

~~~text
Пользователь
    │
    ▼
Приложение
    │
    │ Нужно узнать IP
    ▼
DNS
    │
    │ portal.example.test → 10.0.0.25
    ▼
Приложение
    │
    │ Теперь IP известен
    ▼
Подключение к 10.0.0.25
~~~

То есть разрешение имени происходит **до подключения к серверу**, если нужный ответ ещё не находится в кэше.

Отсюда важный вывод.

Если:

~~~text
10.0.0.25 работает
~~~

но:

~~~text
portal.example.test не работает
~~~

то сама IP-связность может быть исправна, а проблема может находиться именно в DNS.

---

# 4. Кто участвует в DNS-запросе

В DNS участвует не только один «DNS-сервер».

Есть несколько ролей.

## Клиент

Это устройство, которому нужно узнать адрес.

Например:

~~~text
ноутбук пользователя
~~~

## Resolver

Resolver — компонент, который занимается разрешением имён.

Приложение обычно не ищет DNS-записи самостоятельно. Оно обращается к системному resolver.

Упрощённо:

~~~text
Браузер
   │
   ▼
Resolver операционной системы
   │
   ▼
DNS-сервер
~~~

## Рекурсивный DNS-сервер

Такой сервер получает вопрос от клиента и старается получить **готовый конечный ответ**.

Например:

~~~text
Какой IP у example.com?
~~~

Клиент ожидает получить в ответ именно IP или сообщение, что такого имени нет.

Рекурсивный DNS может:

- найти ответ в своём кэше;
- обратиться к другим DNS-серверам;
- вернуть найденный результат клиенту.

## Авторитетный DNS-сервер

Авторитетный сервер хранит **официальные записи определённой зоны**.

Например, сервер может быть авторитетным для:

~~~text
college.test
~~~

и хранить записи:

~~~text
www.college.test
mail.college.test
dns.college.test
~~~

Если его спрашивают про запись из собственной зоны, он отвечает на основании своих данных.

---

# 5. Рекурсивный и авторитетный DNS — в чём разница

Это одна из самых важных идей темы.

## Авторитетный сервер

Он говорит:

> Я отвечаю за эту зону и знаю её записи.

Например:

~~~text
Зона: company.test
~~~

Он может хранить:

~~~text
www.company.test     → 10.10.0.10
mail.company.test    → 10.10.0.20
~~~

## Рекурсивный сервер

Он говорит:

> Если я не знаю ответ, попробую найти его для клиента.

Например, клиент спрашивает:

~~~text
example.com
~~~

Рекурсивный DNS может обратиться к другим DNS-серверам, получить ответ, сохранить его в кэше и вернуть клиенту.

Один физический сервер может выполнять несколько ролей одновременно.

---

# 6. Как DNS устроен в интернете

DNS — распределённая система.

Нет одного единственного сервера, который хранит абсолютно все домены мира.

Система построена иерархически.

Упрощённо:

~~~text
                  Корень DNS
                     .
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
         .ru        .com       .org
          │
          ▼
       example.ru
          │
          ├── www.example.ru
          └── mail.example.ru
~~~

## Корневые DNS-серверы

Они находятся на верхнем уровне и помогают найти серверы доменных зон верхнего уровня.

## TLD

TLD — Top-Level Domain, домен верхнего уровня.

Например:

~~~text
.ru
.com
.org
.net
.test
~~~

## Авторитетные серверы конкретного домена

Они уже знают записи своей зоны.

Упрощённый поиск внешнего имени можно представить так:

~~~text
Клиент
  │
  ▼
Рекурсивный DNS
  │
  ├── спрашивает, где искать нужную зону
  │
  ▼
Авторитетный DNS
  │
  └── возвращает нужную запись
  ▼
Рекурсивный DNS
  │
  ▼
Клиент
~~~

В реальности этапов может быть больше, но для понимания принципа этой схемы достаточно.

---

# 7. Что такое домен и поддомен

Рассмотрим:

~~~text
student.portal.college.test
~~~

Его можно читать справа налево.

~~~text
student . portal . college . test
   │         │         │       │
   │         │         │       └─ верхний уровень
   │         │         └───────── домен
   │         └─────────────────── поддомен
   └───────────────────────────── ещё один уровень имени
~~~

Точка разделяет уровни DNS-иерархии.

Например:

~~~text
college.test
~~~

и:

~~~text
portal.college.test
~~~

— это не два случайных набора слов. Второе имя находится ниже первого в иерархии.

---

# 8. Что такое FQDN

FQDN — Fully Qualified Domain Name, полное доменное имя.

Например:

~~~text
dns.college.test.
~~~

Точка в самом конце обозначает корень DNS.

Полностью имя можно представить так:

~~~text
dns → college → test → .
~~~

В обычной работе завершающую точку часто не пишут:

~~~text
dns.college.test
~~~

Но в DNS-конфигурациях точка может иметь важное значение.

---

# 9. Домен и DNS-зона — не совсем одно и то же

Это часто путают.

## Домен

Домен — часть пространства имён.

Например:

~~~text
company.test
~~~

## DNS-зона

Зона — набор DNS-данных, за которые отвечает конкретный авторитетный сервер.

В простом случае домен и зона выглядят одинаково:

~~~text
Домен: company.test
Зона:  company.test
~~~

Но часть домена можно передать другому DNS-серверу.

Например:

~~~text
company.test
│
├── www.company.test
├── mail.company.test
│
└── students.company.test
~~~

Поддомен:

~~~text
students.company.test
~~~

можно делегировать отдельному DNS-серверу.

Тогда у нас уже будут разные зоны.

Именно поэтому «домен» и «зона» — связанные, но не полностью одинаковые понятия.

---

# 10. Что такое делегирование

Делегирование означает передачу ответственности за часть DNS-пространства другому DNS-серверу.

Например, организация управляет:

~~~text
company.test
~~~

но хочет, чтобы отдельный DNS-сервер отвечал за:

~~~text
students.company.test
~~~

Тогда родительская зона сообщает:

> За students.company.test отвечает другой DNS-сервер.

Для этого используются NS-записи.

На начальном уровне достаточно запомнить:

~~~text
NS → показывает DNS-сервер, отвечающий за зону
~~~

---

# 11. Из чего состоит DNS-запись

Упрощённо DNS-запись содержит:

~~~text
имя    тип    значение
~~~

Например:

~~~text
app.lab.test    A    10.0.0.15
~~~

В реальной DNS-записи также есть TTL и класс.

Полный логический вид:

~~~text
имя    TTL    класс    тип    значение
~~~

Например:

~~~text
app.lab.test.    300    IN    A    10.0.0.15
~~~

Здесь:

| Часть | Значение |
| --- | --- |
| имя | app.lab.test. |
| TTL | 300 секунд |
| класс | IN — Internet |
| тип | A |
| значение | 10.0.0.15 |

В заданиях мы используем сокращённый формат, чтобы сосредоточиться на логике DNS.

---

# 12. A-запись — имя → IPv4

A-запись связывает имя с IPv4-адресом.

~~~text
app.lab.test    A    10.0.0.15
~~~

Читаем так:

> IPv4-адрес app.lab.test — 10.0.0.15.

Схема:

~~~text
app.lab.test
     │
     │ A
     ▼
10.0.0.15
~~~

Если IP сервера изменится, A-запись тоже нужно обновить.

---

# 13. AAAA-запись — имя → IPv6

AAAA похожа на A, но используется для IPv6.

~~~text
app.lab.test    AAAA    2001:db8::15
~~~

Читаем:

> IPv6-адрес app.lab.test — 2001:db8::15.

Запомнить можно так:

~~~text
A     → IPv4
AAAA  → IPv6
~~~

---

# 14. CNAME — одно имя указывает на другое имя

CNAME создаёт псевдоним.

Например:

~~~text
portal.lab.test    CNAME    app.lab.test
~~~

и:

~~~text
app.lab.test       A        10.0.0.15
~~~

Тогда логика такая:

~~~text
portal.lab.test
       │
       │ CNAME
       ▼
app.lab.test
       │
       │ A
       ▼
10.0.0.15
~~~

CNAME не хранит IP напрямую.

Он хранит **другое доменное имя**.

Это удобно, когда несколько имён должны вести к одному основному имени.

Например:

~~~text
portal.lab.test  ─┐
                  ├─→ app.lab.test → 10.0.0.15
lk.lab.test      ─┘
~~~

Если IP сервера изменится, достаточно изменить A-запись основного имени.

---

# 15. MX — какой сервер принимает почту

MX — Mail Exchange.

Запись указывает почтовый сервер домена.

Например:

~~~text
lab.test    MX    10 mail.lab.test
~~~

Число:

~~~text
10
~~~

— приоритет.

Если MX-записей несколько, меньший номер означает более высокий приоритет.

Например:

~~~text
lab.test    MX    10 mail1.lab.test
lab.test    MX    20 mail2.lab.test
~~~

Сначала предпочтителен:

~~~text
mail1.lab.test
~~~

Само имя почтового сервера тоже должно разрешаться в IP.

Например:

~~~text
mail.lab.test    A    10.0.0.20
~~~

Схема:

~~~text
Куда отправлять почту для lab.test?
               │
               ▼
       MX → mail.lab.test
               │
               ▼
       A → 10.0.0.20
~~~

---

# 16. NS — кто отвечает за зону

NS — Name Server.

Запись указывает сервер имён.

Например:

~~~text
lab.test    NS    dns.lab.test
~~~

Это означает:

> DNS-сервером для зоны lab.test является dns.lab.test.

Чтобы обратиться к этому серверу, его имя тоже должно иметь адрес:

~~~text
dns.lab.test    A    10.0.0.2
~~~

Упрощённо:

~~~text
lab.test
   │
   │ NS
   ▼
dns.lab.test
   │
   │ A
   ▼
10.0.0.2
~~~

---

# 17. SOA — основная служебная запись зоны

SOA — Start of Authority.

Она хранит основную служебную информацию о зоне.

Упрощённо в ней находятся данные о:

- главном сервере зоны;
- ответственном лице;
- версии зоны;
- временных параметрах.

Для наших письменных заданий составлять SOA не требуется.

Но важно понимать:

> У нормальной DNS-зоны есть SOA-запись.

Один из важных элементов SOA — **Serial**, номер версии зоны.

Если администратор меняет записи, Serial обычно увеличивают, чтобы другие DNS-серверы могли понять, что зона обновилась.

---

# 18. PTR — обратное разрешение

Обычное разрешение:

~~~text
имя → IP
~~~

Например:

~~~text
server.lab.test → 10.0.0.30
~~~

Это выполняет A-запись для IPv4.

PTR используется наоборот:

~~~text
IP → имя
~~~

Например:

~~~text
10.0.0.30 → server.lab.test
~~~

Такое разрешение называют **reverse DNS** или обратным DNS.

Запомнить:

~~~text
A:   имя → IPv4
PTR: IP   → имя
~~~

PTR-записи хранятся в специальных обратных DNS-зонах.

Для понимания заданий достаточно самой идеи направления поиска.

---

# 19. Короткое имя и полное имя в зоне

В DNS-зоне часто не пишут полное имя каждый раз.

Представим зону:

~~~text
lab.test
~~~

Запись:

~~~text
www    A    10.0.0.10
~~~

внутри этой зоны означает:

~~~text
www.lab.test    A    10.0.0.10
~~~

То же самое:

~~~text
mail    A    10.0.0.20
~~~

означает:

~~~text
mail.lab.test    A    10.0.0.20
~~~

Поэтому в заданиях вы можете увидеть как полные, так и сокращённые имена.

---

# 20. Что такое DNS-кэш

DNS-запросы происходят очень часто.

Если каждый раз заново искать один и тот же адрес, это создаёт лишнюю нагрузку и увеличивает задержку.

Поэтому ответы временно сохраняются в кэше.

Пример:

~~~text
Первый запрос:
Клиент → DNS → app.lab.test → 10.0.0.15

Повторный запрос:
Клиент → кэш → 10.0.0.15
~~~

Кэш может существовать:

- на компьютере пользователя;
- в операционной системе;
- в браузере;
- на рекурсивном DNS-сервере.

---

# 21. Что такое TTL

TTL — Time To Live.

Это время, в течение которого DNS-ответ разрешено хранить в кэше.

Например:

~~~text
TTL = 300
~~~

означает:

~~~text
300 секунд = 5 минут
~~~

Пока TTL не закончился, старый ответ может использоваться повторно.

Это особенно важно при изменении IP.

Было:

~~~text
app.lab.test → 10.0.0.15
~~~

Администратор изменил запись:

~~~text
app.lab.test → 10.0.0.25
~~~

Но клиент ранее сохранил старое значение в кэше.

До истечения TTL он может продолжить использовать:

~~~text
10.0.0.15
~~~

Поэтому DNS-изменения могут становиться заметны не мгновенно.

---

# 22. Что часто называют «распространением DNS»

Можно услышать фразу:

> DNS ещё не распространился.

На практике причина часто связана не с каким-то единым процессом «распространения по всему интернету», а с тем, что разные кэши ещё хранят старые ответы до истечения TTL.

То есть после изменения записи:

~~~text
старый кэш → старое значение
новый запрос после TTL → новое значение
~~~

Для нашего уровня достаточно понимать связь:

~~~text
изменение записи + кэш + TTL
~~~

---

# 23. Что происходит, если записи нет

Если DNS-сервер уверен, что запрашиваемого имени в зоне не существует, клиент может получить ответ:

~~~text
NXDOMAIN
~~~

Это означает:

~~~text
такого доменного имени не существует
~~~

Это отличается от timeout.

## NXDOMAIN

DNS-сервер ответил, но сообщил, что имени нет.

## Timeout

Ответ от DNS-сервера не был получен вовремя.

Причины timeout могут быть другими:

- DNS-сервер недоступен;
- проблема сети;
- порт DNS заблокирован;
- сервер не отвечает.

То есть:

~~~text
NXDOMAIN ≠ timeout
~~~

# 24. Что такое forwarder

Локальный DNS-сервер может знать свои внутренние имена:

~~~text
printer.office.test
files.office.test
~~~

Но пользователь также хочет открыть:

~~~text
example.com
~~~

Локальный DNS может передать такой запрос другому DNS-серверу.

Такой внешний сервер называют **forwarder**, если локальный DNS настроен пересылать ему запросы.

Схема:

~~~text
Клиент
  │
  │ example.com?
  ▼
Локальный DNS
  │
  │ Сам передаёт вопрос дальше
  ▼
Внешний DNS
  │
  ▼
Локальный DNS
  │
  ▼
Клиент
~~~

# 25. Локальные и публичные DNS-зоны

Не все DNS-имена обязаны существовать в публичном интернете.

Организация может иметь локальную DNS-зону, которая работает только внутри её сети.

Например:

~~~text
office.test
~~~

Внутри неё:

~~~text
printer.office.test
files.office.test
db.office.test
~~~

Публичный DNS в интернете о таких именах знать не обязан.

Для учебных примеров мы используем:

~~~text
.test
~~~

.test предназначен для тестирования и документации.

---

# 26. Почему не используем .local

Имя:

~~~text
something.local
~~~

может обрабатываться не обычным DNS.

.local широко используется mDNS — механизмом обнаружения устройств в локальной сети.

Из-за этого обычный DNS и mDNS могут пересекаться.

Чтобы избежать лишней путаницы, в учебных заданиях используем:

~~~text
.test
~~~

---

# 27. DNS и файл hosts

До DNS или вместе с ним операционная система может использовать локальный файл соответствий имён и IP.

Идея файла hosts:

~~~text
10.0.0.15    app.lab.test
~~~

Это локальная запись только на конкретном компьютере.

Разница:

| hosts | DNS |
| --- | --- |
| хранится локально | работает как сетевая служба |
| нужно менять на каждом компьютере | запись можно менять централизованно |
| подходит для нескольких ручных записей | подходит для большого числа устройств |

DNS решает проблему централизованного управления именами.

---

# 28. Типичная последовательность DNS-разрешения

Представим, что пользователь вводит:

~~~text
portal.lab.test
~~~

а существует:

~~~text
portal.lab.test    CNAME    app.lab.test
app.lab.test       A        10.0.0.15
~~~

Последовательность:

~~~text
1. Клиенту нужен portal.lab.test

2. DNS сообщает:
   portal.lab.test → CNAME app.lab.test

3. Теперь нужно разрешить app.lab.test

4. DNS сообщает:
   app.lab.test → A 10.0.0.15

5. Клиент получает итоговый IP:
   10.0.0.15

6. Только после этого клиент подключается к серверу
~~~

Эта цепочка особенно важна для заданий с CNAME.

---

# 29. Как читать DNS-зону

Допустим, дана зона:

~~~text
example.test    NS       dns.example.test
example.test    MX       10 mail.example.test

dns             A        10.20.0.2
www             A        10.20.0.10
mail            A        10.20.0.20
portal          CNAME    www.example.test
~~~

Читаем по строкам.

~~~text
example.test NS dns.example.test
~~~

Значит DNS-сервер зоны называется:

~~~text
dns.example.test
~~~

Дальше:

~~~text
dns A 10.20.0.2
~~~

Так как мы находимся в зоне example.test, короткое имя dns означает:

~~~text
dns.example.test → 10.20.0.2
~~~

Дальше:

~~~text
portal CNAME www.example.test
~~~

означает:

~~~text
portal.example.test
        ↓
www.example.test
~~~

А IP для www.example.test ищем уже в A-записи.

Главный принцип:

> Не пытайтесь угадать ответ по названию. Идите по записям последовательно.

---

# 30. Что произойдёт после изменения IP сервера

Представим:

~~~text
files.lab.test    A    10.0.0.30
~~~

Сервер перенесли:

~~~text
10.0.0.30 → 10.0.0.40
~~~

Если DNS-запись не изменить, клиент продолжит получать:

~~~text
10.0.0.30
~~~

То есть физически сервер может работать отлично, но DNS будет отправлять пользователей на неправильный адрес.

Нужно изменить A-запись:

~~~text
files.lab.test    A    новый IP
~~~

После этого часть клиентов ещё некоторое время может видеть старый IP из-за кэша и TTL.

---

# 31. Почему «по IP работает, по имени нет»

Это одна из самых полезных диагностических ситуаций.

Если:

~~~text
10.0.0.40 → доступен
~~~

а:

~~~text
files.lab.test → не работает
~~~

то мы уже знаем:

- устройство включено;
- IP существует;
- сеть до устройства может работать.

Следующий логичный объект проверки — DNS.

Возможные причины:

- A-запись отсутствует;
- A-запись содержит неправильный IP;
- клиент использует не тот DNS-сервер;
- DNS-сервер недоступен;
- в кэше осталось старое значение.

DNS — не единственная возможная причина любой ошибки, но при рабочем IP и неработающем имени это один из первых компонентов для проверки.

---

# 32. Почему «имя разрешается» ещё не означает, что сервис работает

Обратная ситуация тоже важна.

Если DNS правильно возвращает:

~~~text
site.lab.test → 10.0.0.50
~~~

это доказывает только то, что разрешение имени работает.

Но веб-сайт на этом адресе всё равно может не открываться.

Например:

- веб-сервер выключен;
- нужный порт закрыт;
- приложение не запущено.

Поэтому:

~~~text
DNS работает
~~~

не означает автоматически:

~~~text
веб-сайт работает
~~~

DNS отвечает за поиск адреса, а не за работу самого приложения.

---

# 33. Частые логические ошибки в DNS-записях

## Неверный IP

~~~text
files.lab.test    A    10.0.0.999
~~~

IPv4-октет должен находиться в диапазоне:

~~~text
0–255
~~~

Поэтому 999 недопустимо.

## CNAME ведёт на неправильное имя

~~~text
portal.lab.test    CNAME    unknown.lab.test
~~~

Если целевое имя не имеет нужных записей, цепочка не приведёт к адресу.

## MX указан, но имя почтового сервера не разрешается

Есть:

~~~text
lab.test    MX    10 mail.lab.test
~~~

но нет адреса для:

~~~text
mail.lab.test
~~~

Тогда возникает проблема: известно имя почтового сервера, но неизвестно, где он находится.

## NS указан, но имя DNS-сервера нельзя разрешить

Аналогично, если зона ссылается на:

~~~text
dns.lab.test
~~~

нужно понимать, как получить адрес этого сервера.

---

# 34. DNS как сетевой протокол: порт 53

DNS — это не только набор записей. Это ещё и сетевой протокол.

Обычный DNS использует порт:

~~~text
53
~~~

DNS может работать поверх:

~~~text
UDP 53
TCP 53
~~~

## Почему чаще используется UDP

Большинство обычных DNS-запросов небольшие.

Например:

~~~text
Какой IPv4 у app.lab.test?
~~~

и короткий ответ:

~~~text
10.0.0.15
~~~

Для таких запросов UDP удобен: не нужно заранее устанавливать отдельное соединение.

Упрощённо:

~~~text
Клиент
  │
  │ UDP 53
  ▼
DNS-сервер
  │
  │ ответ
  ▼
Клиент
~~~

## Зачем DNS нужен TCP

TCP тоже является нормальной частью DNS.

Он может использоваться, например:

- когда ответ слишком большой;
- для некоторых специальных DNS-операций;
- при передаче зон между DNS-серверами.

Поэтому неправильно запоминать:

~~~text
DNS = только UDP
~~~

Правильнее:

~~~text
DNS использует и UDP 53, и TCP 53
~~~

Для большинства обычных запросов чаще встречается UDP.

# 35. Рекурсивный и итеративный поиск

Слово «рекурсивный» уже встречалось выше. Теперь разберём его точнее.

## Рекурсивный запрос

Клиент просит:

> Найди мне конечный ответ.

Например:

~~~text
Какой IP у www.example.com?
~~~

Клиент не хочет самостоятельно спрашивать несколько разных DNS-серверов.

Он обращается к рекурсивному DNS и ожидает итог:

~~~text
www.example.com → IP
~~~

или сообщение об ошибке.

Упрощённо:

~~~text
Клиент
  │
  │ Дай конечный ответ
  ▼
Рекурсивный DNS
  │
  │ выполняет поиск
  ▼
Клиент получает результат
~~~

## Итеративный поиск

Во время поиска DNS-сервер может получать не готовый ответ, а подсказку:

> Я не знаю конечный IP, но знаю, какой сервер спросить дальше.

Упрощённый пример:

~~~text
Рекурсивный DNS
      │
      │ Где искать example.com?
      ▼
DNS верхнего уровня
      │
      │ Спроси вот этот авторитетный сервер
      ▼
Рекурсивный DNS
      │
      │ Какой IP у www.example.com?
      ▼
Авторитетный DNS
      │
      │ Вот ответ
      ▼
Рекурсивный DNS
~~~

То есть клиенту обычно нужен **рекурсивный сервис**, а сам DNS-сервер в процессе поиска может выполнять последовательность запросов к другим серверам.

Для начального уровня главное различие такое:

~~~text
рекурсивный запрос → нужен конечный ответ
итеративный ответ  → может указать, куда обратиться дальше
~~~

# 36. Краткая памятка по типам записей

| Тип | Что хранит | Направление |
| --- | --- | --- |
| A | IPv4-адрес | имя → IPv4 |
| AAAA | IPv6-адрес | имя → IPv6 |
| CNAME | другое доменное имя | имя → имя |
| MX | почтовый сервер | домен → mail-сервер |
| NS | DNS-сервер зоны | зона → DNS-сервер |
| PTR | имя для IP | IP → имя |
| SOA | служебные параметры зоны | зона → метаданные |

# Что нужно понимать после выполнения

- DNS связывает доменные имена с IP-адресами.
- DNS-запрос происходит до подключения к серверу по имени.
- A-запись хранит IPv4-адрес.
- AAAA-запись хранит IPv6-адрес.
- CNAME создаёт псевдоним другого имени.
- MX указывает почтовый сервер.
- NS указывает DNS-сервер зоны.
- PTR используется для обратного разрешения IP в имя.
- DNS-зона — часть пространства имён, за которую отвечает DNS-сервер.
- TTL определяет время хранения записи в кэше.
- Из-за кэша изменение DNS может стать заметно не сразу.
- Если соединение по IP работает, а по имени нет, одной из первых нужно проверять DNS.
- Несколько имён могут вести на один сервер.
- DNS-сервер и сервер, на котором работает сайт, — не одно и то же.
